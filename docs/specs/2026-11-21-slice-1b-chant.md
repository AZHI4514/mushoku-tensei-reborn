# 切片 1b · 徒手咏唱

2026-11-21 · 待审

## 玩家体验与范围

徒手按住默认施法键 R，服务端接受请求后，玩家移动变慢，手部持续出现原版水花。持续到咏唱完成，扣除魔力并恢复移动速度；提前松开则中断，保留全部魔力。本片止于咏唱结算。弹体、发射、伤害、命中、自定义粒子和 3D 动画均在范围外。

## 硬约束与数值来源

采用[魔术模块第 5.1 节](../modules/magic.md#51-水属性含冰)的初级水弹 `water_waterball`：消耗 **1**，咏唱 **5 秒**（按 Minecraft 标准速率换算为 **100 个服务端游戏 tick**）。耗时由服务端推进，低 TPS 时实际经过的墙钟时间可以更长。第 3 节已决定咏唱期间降低移动速度，第 7 节规定松键中断不扣魔力。**减速幅度尚未定值，待裁决；本规格只验收确有减速及结束后恢复。**

## 输入与网络协议

客户端注册可重绑的 KeyMapping，默认 R。按下沿发送开始请求，松开沿发送中断请求；持续按住只触发一次咏唱。服务端从连接取得施法者身份，自行读取其魔力并计时。

| 包名与方向 | 内容与处理 |
|---|---|
| `start_chant` · C2S | 请求开始。服务端在待机且魔力充足时接受，重复开始不重置进度，不叠加减速。 |
| `interrupt_chant` · C2S | 请求中断。服务端只中断仍在进行的咏唱；对已结算的咏唱无效。 |
| `chant_state` · S2C | 携带施法者实体标识、服务端状态、总时长 tick 与剩余 tick。开始与终止时发给本人和能观察该实体的客户端；中途开始观察的客户端获得当前剩余 tick。 |

客户端依据总时长和剩余 tick 推进**显示进度**，并按施法者位置维持手部水花。只有服务端可以判定完成、中断、修改移动速度和扣魔力。客户端估算进度即使到达终点，也须等待终态通知。收到中断或完成状态的当帧立即停止生成并清除本次咏唱仍可见的水花，不影响周围自然产生的水花。

## 状态机与职责

纯 Java 状态机位于 `magic/core/`。运行时按玩家分别维护状态，使用服务端 tick 驱动转移；输入包仅表示请求。每次咏唱只能结算一次。

| 当前状态 → 结果 | 服务端条件和动作 |
|---|---|
| 待机 → 咏唱中 | 开始请求有效且魔力至少为 1。开始计时并施加本次咏唱的移动减速，此时不扣魔力。魔力不足时保持待机并提示施法者。 |
| 咏唱中 → 中断 → 待机 | 计满前处理到松键请求，撤销本次减速并广播中断。魔力不扣。死亡、离线时也清理咏唱与减速。 |
| 咏唱中 → 完成 → 待机 | 服务端累计满 100 tick 并确认仍有足够魔力，调用已有 `Mana.spend(current, 1)`，经 1a 的附件写入并同步一次。撤销本次减速并广播完成。若期间魔力被调试命令调到 0，则结束并提示魔力不足，不报告成功。 |

服务端适配层负责读写附件、收发包、应用和移除本次速度修饰。清理时保留其他来源的速度效果。客户端输入与粒子表现限定在物理客户端。粒子使用 `minecraft:splash`，跟随施法者手部，本片不产生飞行物。

## 验收

1. WHEN A 徒手按住 R 且魔力充足，SHALL 在服务端接受后进入咏唱。A 和附近的 B 都能看到 A 手部的水花；同一段平地上，A 按相同移动输入时比待机时慢。
2. WHEN 管理员用 1a 命令将 A 设为 37，再执行 `/mushoku mana get A`，SHALL 读到 **37 / 100**。A 按住 R 完成一次咏唱后再次执行同一 get，SHALL 读到 **36 / 100**。继续按住不应产生第二次扣费；场上没有弹体或命中效果。
3. WHEN A 从 37 点开始咏唱并在 100 tick 前松开 R，SHALL 在服务端确认中断后立即消除双方画面中的本次水花，恢复移动速度。等到原定完成时间后 get 仍为 **37 / 100**。
4. WHEN 服务端完成一次完整咏唱，SHALL 撤销该次减速、结束粒子表现并返回待机；再次松开再按下可开始下一次咏唱。
5. WHEN A 魔力为 0 时按 R，SHALL 收到魔力不足提示，保持待机，移动速度不变，双方都看不到咏唱水花。
6. WHEN 服务端暂停 tick 而客户端继续绘制，SHALL 保持服务端咏唱状态和魔力；恢复服务端 tick 并累计到规定时长后才完成扣费。测试时可用管理员 tick 冻结与步进核对完成边界。

L2 以纯 Java 测试覆盖开始、重复请求、中断、完成边界及单次结算；联机验收核对请求方向、旁观表现、移动速度恢复和命令读数。
